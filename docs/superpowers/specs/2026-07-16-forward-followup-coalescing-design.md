# 转发后补充说明合并设计

## 背景与证据

用户在飞书话题群中转发一段内容并补充说明时，飞书会连续投递两条顶层消息。botmux 当前立即处理第一条消息并创建话题，随后又把第二条消息当成另一条新会话，因此出现两个话题和两张仓库选择卡。

在群 `oc_656712339f44a8b537fcd64fa9b63440` 的只读消息记录中观察到两组相同事件形态：

- 2026-07-16 10:21:45.087：第一条消息 `om_x100b6ab04d435ca0b12dc02d2e2f1a8`；10:21:45.421：补充说明 `om_x100b6ab04d5958b8c1c6d35cd43494b`，间隔 334ms。后者的 `root_id`、`parent_id` 均指向前者。
- 2026-07-16 10:25:26.955：第一条消息 `om_x100b6ab05fa660a8b3c96796960d79a`；10:25:27.312：补充说明 `om_x100b6ab05fbea4a8c1f37f014d412de`，间隔 357ms，ID 关系相同。

第一组的首条消息类型是普通 `text`，第二组才是 `merge_forward`。因此不能仅凭 `msg_type` 判断“转发内容”，也不应使用长度或文本相似度等不可靠启发式规则。

## 目标行为

话题群中一条本来要创建新会话的用户消息先进入短暂等待窗口：

1. 若窗口内收到同一 Lark App、同一群、同一发送者的后续消息，且后续消息的 `root_id` 精确等于首条消息的 `message_id`，两条消息合并为一次会话输入。
2. 会话锚点使用后续消息的 `message_id`，机器人卡片和文本回复均出现在后续补充说明所开启的话题中。
3. CLI 输入按“首条完整内容（含转发树）→ 后续补充说明”的顺序组织，并合并两条消息中的图片、文件和 mention 元数据。
4. 若等待窗口到期仍未匹配，首条消息按原有逻辑正常创建会话。

## 等待时间配置

新增环境变量 `BOTMUX_FORWARD_FOLLOWUP_WAIT_MS`：

- 默认 `1500` 毫秒。
- `0` 表示关闭等待与合并，恢复原有即时处理行为。
- 正数限制在 `1..10000` 毫秒，超过上限按 `10000` 处理；无效值回退到默认值。

配置属于飞书事件传输层的全局时序参数，不加入 per-bot `bots.json` 或 Dashboard，避免不同机器人在同一条转发动作上使用不一致窗口。

## 架构

### 1. 纯状态协调器

新增 `src/im/lark/forward-followup-buffer.ts`，负责管理待处理首条消息。协调器只处理以下数据：App、群、发送者、首条消息 ID、定时器和待执行回调，不解析飞书正文，也不直接创建会话。

它提供三个行为：

- `hold`：暂存符合条件的新话题种子，启动等待计时器。
- `match`：按 `root_id` 找到待处理种子，并再次核对 App、群和发送者；成功后原子移除种子、取消计时器，返回配对数据。
- `flush`：超时后原子移除种子并执行原始分发；关闭 dispatcher 时可清理全部计时器。

待处理项直接以首条 `message_id` 建索引。App、群、发送者作为二次校验，防止跨群或跨用户错误合并。

### 2. Event Dispatcher 集成

延迟只应用于以下消息：

- 人类发送；
- 群聊当前确认为话题群；
- 路由结果是以当前 `message_id` 为锚点的全新 thread-scope 会话；
- 已通过原有授权和 mention gate；
- 不是 slash command、workflow command 或其他已被前置拦截的控制消息。

普通群、私聊、已有 thread 回复、bot-to-bot 消息、卡片动作及文档/会议事件不进入缓冲。

后续消息在权限判定前可用 `root_id` 探测已通过权限校验的待处理种子。匹配成功时，后续消息继承这次用户动作的准入结果，但仍必须满足同 App、群、发送者约束；随后以 `scope='thread'`、`anchor=后续 message_id` 进入一次 `handleNewTopic`。

原有 `serializeByAnchor` 保留，且只在超时分发或配对完成后调用，避免缓冲期间创建任何 session 或回复。

### 3. Daemon 内容合并

在 `RoutingContext` 中增加可选的首条事件字段。`handleNewTopic` 继续以第二条事件作为主事件：

- 正常解析第二条正文、sender、命令及回复落点；
- 额外解析首条事件；若首条是 `merge_forward`，沿用现有 `expandMergeForward` 展开完整转发树；
- 将首条正文置于第二条正文之前；
- 合并资源列表，沿用现有下载与附件提示流程；
- 不再为第二条生成重复 quote hint，因为首条内容已显式进入 prompt。

会话标题优先使用后续补充说明，使话题列表体现用户真正提出的任务，而不是长篇转发正文的开头。

## 并发、失败与生命周期

- `match` 与超时 `flush` 对同一待处理项只允许一个成功，防止双分发。
- 若 daemon 在等待期间退出，内存中的消息不会被处理；这与当前事件正在进程内处理时崩溃的语义一致，飞书事件重投仍由现有 event claim/dedup 机制处理。
- 若首条转发展开失败，沿用现有降级内容，不影响后续补充说明创建会话。
- 窗口超时后才到达的后续消息保持现有路由行为，不撤回已经发送的首话题卡片，也不迁移运行中的 session。
- 同一用户并行转发多条内容时按各自首条 `message_id` 独立匹配，不共享计时器。

## 测试

### 配置测试

- 未设置时返回 1500ms。
- `0` 关闭功能。
- 有效正数透传。
- 非数字、负数回退默认值；超过 10000ms 截断。

### 协调器单元测试

- 334ms/357ms 形态的 `root_id` 后续成功匹配，只分发一次。
- 超时后单独分发首条。
- 不同发送者、不同群、不同 App 不匹配。
- 匹配与超时竞争时仍只分发一次。
- 多个并行首条消息按 message ID 独立配对。

### Dispatcher 回归测试

- 话题群新会话延迟到窗口结束。
- 关联后续消息以后者 ID 作为新锚点，并携带首条事件。
- 普通群、p2p、已有 thread 回复、命令路径不增加延迟。
- 功能关闭时维持即时分发。

### Daemon/内容测试

- 普通 `text` 首条与后续说明合并，顺序正确。
- `merge_forward` 首条被展开后与说明合并。
- 两条消息的附件都进入同一次 prompt。
- 标题取后续说明，回复锚点取后续 message ID。

## 影响范围

- 仅影响 Lark 话题群中新建会话的首条人类消息；所有 CLI 和后端共享同一输入，因此无需为不同 CLI/backend 分支实现。
- 普通群、p2p、已有会话续聊、adopt/restore、workflow、卡片动作、其他 IM 平台不改变。
- 开启默认配置后，受影响的新话题首响最多增加 1.5 秒；可通过环境变量调节或设为 0 回退。
